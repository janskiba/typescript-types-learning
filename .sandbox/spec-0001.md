# Specyfikacja lekcji 0001 — „Enum czy unia literałów?"

Język: polski. Ton: prosty, konkretny, zero lania wody. Każdy blok ma mieć ~1 myśl.
Kontekst czytelnika: mid-level TS, pracuje w zespole, chce rozumieć wybory typów w code review.
Zasada: kod krótki, komentarze w kodzie po polsku, każdy przykład pokazuje błąd albo konsekwencję.

## KONTEKST ŚRODOWISKA (ważne dla przykładów)
- Uczeń ma lokalnie **TypeScript 7.0.2**, tryb `strict`.
- Wszystkie poniższe zachowania ZWERYFIKOWANE kompilatorem (tsc 7.0.2, `strict`) — nie zmieniaj ich, chyba że podano inaczej.

## Cel lekcji (jeden zwrot)
Enum to nie jest "typ". Enum to obiekt runtime + osobny (nominalny) typ.
Wszystkie spory o enumy w review wynikają z niezrozumienia jednej rzeczy:
TypeScript ma dwa światy — typy (znikają po kompilacji) i wartości (istnieją w runtime).

## Struktura lekcji (sekcje w tej kolejności)

### 1. Hook — prawdziwy diff z review
```ts
// PR: "dodaje statusy zadań"
enum TaskStatus {
  Todo = 'todo',
  InProgress = 'in_progress',
  Done = 'done',
}
```
Pytania do czytelnika (przed odpowiedzią):
- "Co tu jest właściwie: typ, wartość, czy oba?"
- "Co się stanie, jak ktoś napisze `const s: TaskStatus = 'todo';`?"
Odpowiedź dopiero w sekcji 3/4 (hook nie może zdradzać odpowiedzi wizualnie).

### 2. Dwa światy TypeScriptu
- Typy (`type`, `interface`, unie) — znikają po kompilacji, w runtime nie ma ich w ogóle.
  Dowód: `console.log(typeof (undefined as unknown as TaskStatusUnion))` → `undefined`.
- Wartości (`const`, obiekty, funkcje, klasy, enumy) — istnieją w runtime.
- Enum to rzadki przypadek, który jest jednocześnie typem i wartością.
  Dowód: `console.log(typeof TaskStatus)` → `object`, `console.log(TaskStatus)` → `{ Todo: 'todo', ... }`.

### 3. Co enum naprawdę jest
Typ: `TaskStatus` = unia **własnych** członków (`TaskStatus.Todo | TaskStatus.InProgress | TaskStatus.Done`) — NIE unia surowych stringów.
Wartość: zwykły obiekt runtime `{ Todo: 'todo', InProgress: 'in_progress', Done: 'done' }`.

### 4. KLUCZOWA RÓŻNICA (to jest serce lekcji)
Zweryfikowane:
```ts
enum TaskStatus { Todo = 'todo', Done = 'done' }
type TaskStatusUnion = 'todo' | 'done';

const a: TaskStatusUnion = TaskStatus.Todo; // ✅ OK — element enumu to string 'todo'
const b: TaskStatus = 'todo';                // ❌ BŁĄD TS2322 — surowy string NIE pasuje do typu enumu
const c: TaskStatusUnion = 'todo';           // ✅ OK
```
Wniosek do zapamiętania: **enum tworzy typ nominalny.** Do zmiennej typu enum trzeba włożyć element enuma.
Unia literałów jest typem strukturalnym — przyjmuje surowy string.
To oznacza w praktyce: enum = kontrola "wejścia" (nikt nie wrzuci dowolnego stringa), unia = wygodna współpraca z danymi z API/JSON.
Przykład z błędem do przeczytania:
```ts
// dane z API (string) → nie wejdzie do enuma bez rzutowania
const fromApi = JSON.parse('{"status":"todo"}') as { status: TaskStatus }; // ⛔ kłamstwo, które TS akceptuje
```

### 5. Trzy sposoby na ten sam zestaw wartości
a) Union-only:
```ts
type TaskStatus = 'todo' | 'in_progress' | 'done';
```
b) Enum:
```ts
enum TaskStatus { Todo = 'todo', InProgress = 'in_progress', Done = 'done' }
```
c) Obiekt `as const` + typ wyliczony:
```ts
const TaskStatus = { Todo: 'todo', InProgress: 'in_progress', Done: 'done' } as const;
type TaskStatus = (typeof TaskStatus)[keyof typeof TaskStatus];
```
Tabela porównawcza (kolumny): "wartość w runtime?", "surowy string przechodzi?", "ile linii kodu", "co z `Object.values` / iteracją", "ryzyko".

### 6. Reguły decyzyjne (serce lekcji) — tabela
| Sytuacja | Wybór |
|---|---|
| Tylko typ, status nigdy nie jest wartością | unia literałów |
| Potrzebuję obiektu w runtime (iteracja, mapowanie na labelki, `Object.values`) | enum (string) albo obiekt `as const` |
| Zestaw zamknięty i znany | unia lub enum |
| Zestaw przyjdzie z zewnątrz (API) | unia + walidacja w runtime |
| Wartość trafi do bazy/JSON | string enum — zmiana wartości = breaking change |
| Zwykłe flagi/stany (bitowe) | enum liczbowy, świadomie |

### 7. Pułapki (każda: 1 zdanie + mikro-przykład, wszystkie zweryfikowane)
1. **Reverse mapping działa tylko dla liczb.**
   Zweryfikowane: `NumEnum[0] === 'Low'` i `NumEnum['Low'] === 0`; dla stringowego: `StrEnum['todo'] === undefined` (brak odwrotnego mapowania).
2. **Enum liczbowy przyjmuje surową liczbę** — `const d: NumEnum = 0;` przechodzi (zweryfikowane). Tracisz ochronę typu; do tego numery zmieniają się przy wstawieniu elementu w środek.
3. **`const enum` (i zwykły `enum`) nie przejdą przez `erasableSyntaxOnly`** — TS 5.8+ (zweryfikowane: TS1294 "This syntax is not allowed when 'erasableSyntaxOnly' is enabled"). Babel/transpile-only też nie ogarnia `const enum` (TS podstawia wartości w miejscu użycia). Praktyka: nie używaj `const enum`.
4. **`typeof TaskStatus` to typ OBIEKTU, nie typ statusu.** `const x: typeof TaskStatus = TaskStatus` — a `const y: TaskStatus = TaskStatus` to błąd.
5. **String enum to wartość, która trafia do bazy/JSON** — zmiana `'todo'` na `'TODO'` to breaking change danych, nie tylko kodu.

### 8. Quiz (interaktywny, natychmiastowy feedback)
6 pytań, KAŻDA odpowiedź ma identyczną liczbę słów (bez wskazówek formatowaniem):
1. Co istnieje w runtime dla `type Status = 'todo' | 'done'`? → nic / obiekt / enum
2. `const s: Status = 'todo'` gdzie `Status` to enum → OK / błąd / działa w enumie liczbowym
3. Odwrócone mapowanie działa dla → enumów liczbowych / enumów stringowych / obu
4. `erasableSyntaxOnly` blokuje → tylko const enum / każdy enum / enum liczbowy
5. `as const` robi głównie → readonly / wymusza runtime / dodaje opcjonalność
6. Co bezpieczniej dla wartości leczącej do bazy → string enum / enum liczbowy / unia literałów

### 9. Micro-ćwiczenie "review"
Trzy kawałki kodu z zespołu; zadanie: wybierz enum / unia / `as const` + uzasadnij jednym zdaniem.
Klikalne warianty z natychmiastowym feedbackiem (prawidłowa odpowiedź + dlaczego + co powiedzieć w review).
