Lekcja 0001

Enum czy unia literałów?

1. Hook — prawdziwy diff z review

Patrzysz na PR. Ktoś dodaje statusy zadań:

// PR: "dodaje statusy zadań"
enum TaskStatus {
  Todo = 'todo',
  InProgress = 'in_progress',
  Done = 'done',
}

Zatrzymaj się nad dwoma pytaniami, zanim przeczytasz dalej:

  • Co tu jest właściwie: typ, wartość, czy oba?
  • Co się stanie, jak ktoś napisze const s: TaskStatus = 'todo';?

Odpowiedzi znajdziesz w sekcjach 3 i 4.

2. Dwa światy TypeScriptu

TypeScript działa w dwóch światach. Typy znikają po kompilacji. Wartości zostają w runtime.[8]

type TaskStatusUnion = 'todo' | 'done';

// Typy znikają po kompilacji — w runtime nie ma ich wcale.
console.log(typeof (undefined as unknown as TaskStatusUnion)); // undefined

Enum jest rzadkim przypadkiem: jest jednocześnie typem i wartością.

enum TaskStatus {
  Todo = 'todo',
  InProgress = 'in_progress',
  Done = 'done',
}

// Enum istnieje w runtime jako zwykły obiekt.
console.log(typeof TaskStatus); // object
console.log(TaskStatus);
// { Todo: 'todo', InProgress: 'in_progress', Done: 'done' }

3. Co enum naprawdę jest

Typ TaskStatus to unia własnych członków enumu:

TaskStatus.Todo | TaskStatus.InProgress | TaskStatus.Done

To nie jest unia surowych stringów, takich jak 'todo' | 'done'.[1][7]

Wartość enumu to natomiast zwykły obiekt runtime:

{ Todo: 'todo', InProgress: 'in_progress', Done: 'done' }

4. Kluczowa różnica

To jest serce lekcji. Sprawdź to sam w edytorze:

enum TaskStatus { Todo = 'todo', Done = 'done' }
type TaskStatusUnion = 'todo' | 'done';

const a: TaskStatusUnion = TaskStatus.Todo; // ✅ OK
// @ts-expect-error TS2322 — surowy string nie pasuje do typu enumu.
const b: TaskStatus = 'todo';               // ❌ błąd
const c: TaskStatusUnion = 'todo';          // ✅ OK
Wniosek

Enum tworzy typ nominalny. Do zmiennej typu enum musisz włożyć element enumu. Unia literałów jest typem strukturalnym — przyjmuje surowy string.[2]

W praktyce enum = kontrola „wejścia” (nikt nie wrzuci przypadkowego stringa). Unia = wygodna współpraca z danymi z API i JSON.

enum TaskStatus {
  Todo = 'todo',
  InProgress = 'in_progress',
  Done = 'done',
}

// Dane z API przychodzą jako string. To `as` kłamie kompilatorowi.
const fromApi = JSON.parse('{"status":"todo"}') as { status: TaskStatus };

To działa, ale jest niebezpieczne. Lepiej użyć unii i sprawdzić wartość w runtime.

5. Trzy sposoby na ten sam zestaw wartości

a) Tylko unia:

type TaskStatus = 'todo' | 'in_progress' | 'done';

b) Enum:

enum TaskStatus {
  Todo = 'todo',
  InProgress = 'in_progress',
  Done = 'done',
}

c) Obiekt as const z typem wyliczonym:

const TaskStatus = {
  Todo: 'todo',
  InProgress: 'in_progress',
  Done: 'done',
} as const;

type TaskStatus = (typeof TaskStatus)[keyof typeof TaskStatus];
Kryterium Unia Enum stringowy as const
Wartość w runtime? nie ma obiekt obiekt
Surowy string przechodzi? tak nie tak
Ile linii kodu 1 4 2 + typ
Object.values / iteracja nie tak tak
Ryzyko niskie const enum, reverse mapping literówka w kluczu

6. Reguły decyzyjne

Sytuacja Wybór
Tylko typ, status nigdy nie jest wartością unia literałów
Potrzebuję obiektu w runtime (iteracja, mapowanie na labelki, Object.values) enum stringowy albo obiekt as const
Zestaw zamknięty i znany unia lub enum
Zestaw przyjdzie z zewnątrz (API) unia + walidacja w runtime
Wartość trafi do bazy / JSON string enum — zmiana wartości to breaking change
Zwykłe flagi / stany bitowe enum liczbowy, świadomie

7. Pułapki

1. Reverse mapping działa tylko dla liczb.
enum NumEnum { Low = 0, High = 1 }
enum StrEnum { Todo = 'todo' }

// Reverse mapping działa tylko dla enumów liczbowych.
console.log(NumEnum[0]);      // 'Low'
console.log(NumEnum['Low']);  // 0
// @ts-expect-error — string enum nie ma właściwości 'todo'.
console.log(StrEnum['todo']); // undefined (brak reverse mappingu)

Dla enumu stringowego odwrotnego mapowania nie ma.[3]

2. Enum liczbowy przyjmuje surową liczbę.
enum NumEnum { Low = 0, High = 1 }

// Surowa liczba pasuje do enumu liczbowego.
const d: NumEnum = 0; // ✅ OK, ale tracisz ochronę typu.

Każda liczba typu number wejdzie. Do tego numery zmieniają się, gdy ktoś wstawi element w środek enumu.

3. const enum może wybuchnąć w buildzie.
// const enum znika w trakcie kompilacji.
const enum Size { Small = 1, Large = 2 }

// Nie przejdzie z `--erasableSyntaxOnly`.
// Przy `isolatedModules` też może się zepsuć, bo transpile-only
// (np. Babel, SWC, esbuild) nie wstawi wartości w miejsce użycia.

TypeScript Handbook pisze, że const enum jest niezgodny z isolatedModules, a narzędzia transpile-only nie potrafią go zinline'ować. Praktyka: nie używaj const enum.[4][5][6]

4. typeof Enum to typ obiektu, nie typ statusu.
enum TaskStatus { Todo = 'todo', Done = 'done' }

// `typeof TaskStatus` to typ obiektu, nie typ statusu.
const x: typeof TaskStatus = TaskStatus; // ✅ OK
// @ts-expect-error TS2741 — typ obiektu to nie unia członków.
const y: TaskStatus = TaskStatus;        // ❌ błąd

Sam enum (bez typeof) to typ unii członków. typeof Enum to typ obiektu runtime.

5. String enum to wartość, która trafia do bazy i JSON.
enum TaskStatus { Todo = 'todo' }

// Zmiana wartości stringowej to breaking change w bazie / JSON.
// `Todo = 'TODO'` zmieni zapisane dane, a nie tylko nazwę w kodzie.

Dlatego wartości enumu traktuj jak publiczne API.

10. Ściąga i zamknięcie

Ściąga do wydruku

Zachowaj pod ręką: ściąga: typy i enumy.

Co zapamiętać

  • Enum to typ nominalny — do zmiennej typu enum wkładasz element enumu, a nie surowy string.
  • Unia literałów to tylko typ; znika po kompilacji i dobrze współpracuje z danymi z API.
  • Unikaj const enum — może się zepsuć przy isolatedModules i --erasableSyntaxOnly.
